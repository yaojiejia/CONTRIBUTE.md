# Artifact conventions

Shared rules for every file the `repo-intel` skills generate. Read once per session; all six skills depend on these.

## Location

All artifacts live in `.repo-intel/` at the **target repo's root** — never in the plugin directory, never in a system temp directory.

```
<repo-root>/.repo-intel/
├── REPO-MAP.md                       # repo-map
├── LESSONS.md                        # repo-lessons
├── issues/
│   ├── CANDIDATES.md                 # issue-hunt, phase A
│   └── <number>-analysis.md          # issue-hunt, phase B
├── optimizations/
│   └── OPT-<YYYY-MM-DD>.md           # opt-scan
├── features/
│   ├── DEMAND-<YYYY-MM-DD>.md        # feature-scan, stated demand
│   └── FEAT-<YYYY-MM-DD>.md          # feature-scan, ranked proposals
└── bugs/
    └── BUG-<YYYY-MM-DD>.md           # bug-scan, verified findings and ledger
```

`.repo-intel/` is hidden from git via `.git/info/exclude`, which `scripts/intel_init.sh` maintains. **Never add `.repo-intel/` to the repo's tracked `.gitignore`** — that would be a source change in someone else's repo, and it would show up in a PR. The artifacts must never appear in `git status`, a diff, or a pull request.

## Bootstrap

Every skill starts by running:

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/intel_init.sh"
```

It is idempotent — safe on every run. It returns JSON with `repo_root`, `intel_dir`, `slug`, `head_sha`, `branch`, `default_branch`, and an `artifacts` map showing which files already exist. Use `head_sha` for the provenance footer and `artifacts` to decide between a first-time generation and an incremental update.

If it returns `{"ok": false, ...}` the directory is not a git repository. Say so plainly and stop; these skills need git history and a repo root to be useful.

## Provenance footer

Every generated file ends with exactly this block:

```markdown
---
<!-- repo-intel provenance -->
- **Generated by:** repo-intel/<skill-name> v<skill-version>
- **Commit:** <head_sha>
- **Generated:** <YYYY-MM-DD HH:MM UTC>
- **Regenerate with:** /repo-intel:<skill-name>
```

The commit SHA is what makes staleness detectable. Never omit it.

## Staleness and incremental updates

When a skill runs and its artifact already exists, do not regenerate from scratch. Instead:

1. Read the recorded commit SHA from the existing footer.
2. Run `git diff --stat <recorded-sha>..HEAD` to see what moved.
3. If the SHA is unreachable (force-push, shallow clone), fall back to a full regeneration and say so.
4. If nothing relevant changed, report that the artifact is current and stop — do not rewrite a file to change only its timestamp.
5. Otherwise update only the affected sections, then refresh the footer.

Preserve human edits. If a section looks hand-written (content that no skill would produce), keep it and note the conflict rather than overwriting it.

## Writing style for artifacts

These files are read by a person in a hurry and by a future Claude session with no context. Both are served by the same things:

- **Anchor every claim to evidence.** Cite `path/to/file.py:88`, not "the serializer". A claim with no file reference is a guess and must be labeled as one.
- **Separate observed from inferred.** Mark anything not directly verified: `(inferred)`, `(unverified)`, `(assumed — not run)`. A confidently stated wrong fact is worse than an acknowledged gap, because the next session inherits it.
- **Lead with the answer.** Tables and short declaratives over prose paragraphs.
- **Say what is missing.** An "Open questions" section is a feature; silence about gaps is not.
