# Lessons protocol

The full specification for `.repo-intel/LESSONS.md` — the ledger that makes the other three skills get better at a repo over time instead of re-deriving the same wrong assumptions every session.

## Why this file exists

Every session in an unfamiliar repo makes the same class of mistake: assuming the test command, assuming where a module lives, assuming a config is respected when it is overridden elsewhere. The mistake is discovered, corrected, and then forgotten when the session ends. LESSONS.md is where a correction is written down once so it is never paid for twice.

The failure mode this protocol exists to prevent is an append-only log that grows until nobody reads it. **Dedupe and promotion are not optional polish — they are what keeps the file worth reading.**

## File structure

```markdown
# Lessons — <repo slug>

Corrections learned while working in this repo. Read the index before starting work;
read a full entry only when its subject is relevant to the task at hand.

## Index

- **build-system** — root `test` script is a no-op; real command is `pnpm -w test:unit`
- **api-auth** — middleware order matters; auth runs after body parsing, not before
- **codegen** — `src/generated/` is committed but regenerated by `make proto`; never hand-edit

---

## 2026-08-23 — wrong test runner assumed
...full entry...

## 2026-08-19 — auth middleware order
...full entry...
```

The index is the point. It stays cheap enough to read on every single run, and it makes a full entry read a deliberate, targeted act rather than a whole-file load. One line per entry, newest first, phrased as the conclusion — not the title.

## Entry schema

```markdown
## <YYYY-MM-DD> — <short title>
**Confusion:** What was assumed, and what turned out to be true instead.
**Signal that would have caught it:** The observable fact that was available all along.
**Rule:** The generalized directive for next time.
**Refs:** `path/file.ext:line`, [[other-lesson]]
```

Each field earns its place:

- **Confusion** — the specific wrong belief. Not "there was an error" but "assumed X, actually Y".
- **Signal** — the most valuable field, and the one most often written lazily. It answers: *what could have been read, and where, that would have prevented this?* A lesson whose signal is "there was no way to know" is worth keeping only if the rule is "ask the user about this".
- **Rule** — imperative, general enough to fire in a similar-but-not-identical situation, specific enough to act on. "Be careful with tests" is useless. "Read `turbo.json` before inferring test commands in a monorepo" is a rule.
- **Refs** — file paths with lines, and `[[wiki-links]]` to related lesson subjects. A `[[link]]` to a lesson that does not exist yet is fine; it marks a gap worth filling.

## When to write an entry

Write when any of these happen:

1. **The user corrects a wrong assumption.** The highest-value trigger. If the user says "no, it's actually X" — that is a lesson, every time.
2. **A command, build, or test fails because of a guess.** Not any failure — a failure caused by acting on an unverified belief.
3. **A run dead-ends.** Time was spent going the wrong direction and the reason is now known.
4. **A finding contradicts REPO-MAP.md.** The map is wrong; record the correction and fix the map.
5. **Something non-obvious was discovered that cost real effort to learn** — an implicit invariant, a load-bearing side effect, a config that silently overrides another.

## When not to write an entry

Restraint here is what keeps the file readable:

- Anything already stated in `REPO-MAP.md`, `CLAUDE.md`, `CONTRIBUTING.md`, or the README. Those are already loaded; duplicating them adds noise.
- A restatement of an error message. The lesson is the *cause*, never the traceback.
- One-off facts with no future bearing — a transient network failure, a typo already fixed.
- Anything derivable in seconds from the code. `git log` and `rg` are cheaper than a stale note.
- Speculation. Only record what was actually observed to be true.

## Dedupe before appending

Never append without checking first:

```bash
rg -i '<subject keywords>' .repo-intel/LESSONS.md
```

Then choose:

- **No match** → append a new entry, add its index line.
- **A near-match exists** → **sharpen the existing entry instead of adding a second one.** Broaden its Rule to cover both cases, add the new `file:line` to Refs, and update its date. Two entries about the same subject is the beginning of the decay this protocol exists to prevent.
- **A match exists and the new information contradicts it** → the newer observation wins. Rewrite the entry, and add a line `**Superseded:** <what the old entry claimed, and why it was wrong>`. Preserving the reversal matters: it prevents flip-flopping back to the original wrong belief later.

## Promotion

A lesson is a note about a mistake. A gotcha is a permanent property of the repo. When a rule has proven stable and general — it has fired more than once, or it is plainly a fixed fact about how the repo works — promote it:

1. Add it to the **Gotchas** section of `REPO-MAP.md`.
2. Mark the lesson entry: `**Status:** promoted → REPO-MAP.md#gotchas`.
3. Leave the entry in place. Do not delete it — the record of *how* it was learned is what stops it being re-litigated.

Promoted lessons stay in the index but move below unpromoted ones, since the map now carries them.

## Contradiction handling

When a lesson conflicts with `REPO-MAP.md`, **the lesson wins.** It is newer and it was born from an actual failure, while the map section was a generalization. Fix the map, and note the correction in the lesson's Refs.

## Read protocol — how the other skills use this

Every skill opens with:

1. Read `.repo-intel/LESSONS.md` if it exists. **Read the index section only.**
2. Scan the index for lines whose subject touches the current task.
3. Read the full entries for those lines, and only those.
4. When a lesson's Rule applies to a step about to be taken, follow it and say so briefly — "LESSONS.md says the root `test` script is a no-op, using `pnpm -w test:unit`". Visibly acting on a lesson is how the user learns to trust the ledger.

If the file does not exist, proceed normally and create it on the first entry worth writing.

## Reflection step — how the other skills close

At the end of any repo-intel run, spend one pass asking: *did anything in this run turn out other than expected?* If yes, and it meets a write trigger above, record it. If nothing did, write nothing — a run that produces no lesson is the normal case, and forcing an entry to feel productive actively degrades the file.
