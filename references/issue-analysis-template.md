# Issue analysis template

Structure for `.repo-intel/issues/<number>-analysis.md`, produced by phase B of `issue-hunt`.

The purpose is to reach the point where implementation is mechanical: the cause is located, the fix is chosen, the tests are identified, and the project's contribution rules are known. An analysis that restates the issue in more words has done nothing.

---

```markdown
# Issue #<number> — <title>

<url> · opened <date> by <author> · labels: `bug`, `gh-issue`

## What is being asked

Two or three sentences in plain terms. Separate what the reporter *asked for* from
what they actually *need* — these differ often, and the maintainers' comments are
usually where the real requirement is stated.

## Acceptance criteria (inferred)

What must be true for a PR to close this. Mark each as stated or inferred.

- [ ] `gh issue list --limit 150` issues exactly 2 API pages, not 3 *(stated in issue body)*
- [ ] Existing `--search` behavior unchanged *(inferred — no maintainer statement)*

## Reproduction

The exact commands, and whether they were actually run.

```bash
$ gh issue list --repo cli/cli --search "sort:created" --limit 150
```

**Result:** confirmed — 3 requests issued (observed via `GH_DEBUG=api`).
**Or:** not reproduced — requires a GitHub Enterprise host, unavailable here.

Never present an unrun reproduction as confirmed. "Not reproduced, because X" is a
legitimate and useful outcome.

## Root cause

The trace from symptom to cause, with real line references.

1. `pkg/cmd/issue/list/list.go:88` passes `opts.LimitResults` to the API layer
2. `api/queries_issue.go:210` computes `perPage = min(limit, 100)`
3. `api/queries_issue.go:224` loops `while fetched < limit`, but the search endpoint
   returns `total_count`, not a cursor — so the final iteration fires even when the
   previous page already satisfied the limit

**The defect:** the loop condition tests `fetched < limit` before checking whether
the previous response was a short page.

If the cause cannot be located, say so explicitly and list what was ruled out. A
wrong root cause is more expensive than an absent one.

## Blast radius

What else touches this code, from an actual `rg` sweep — not from memory.

| Caller | File | Risk if changed |
|---|---|---|
| `gh pr list` | `pkg/cmd/pr/list/list.go:64` | Shares the pagination helper; must not regress |

## Prior art

Previous attempts and why they did not land. For an issue flagged
"prior attempt closed unmerged", this section is the most valuable one in the file.

- **PR #13913** (closed, unmerged) — fixed the loop but broke `--limit 0`;
  maintainer asked for a test and the author did not return.
- `git log -S "perPage" --oneline -- api/queries_issue.go` shows this logic was last
  touched in `a3f21bc` for a different pagination bug.

## Fix options

Two or three real options with honest trade-offs, then a recommendation.

### Option A — short-circuit on a short page *(recommended)*
Break the loop when a response returns fewer items than `perPage`.
- **Pro:** three lines; matches how the REST paginator already behaves
- **Con:** does not help the `search` endpoint's `total_count` inconsistency

### Option B — compute page count up front
- **Pro:** removes the loop entirely
- **Con:** rewrites a helper shared with `gh pr list`; larger review surface

## Test plan

**Existing coverage:** `api/queries_issue_test.go:301` covers limits under 100 only —
which is why this shipped.

**New tests needed:**
- `TestIssueList_LimitExceedsPageSize` — asserts request count for `--limit 150`
- Table case for `--limit` exactly 100 (the boundary the current code gets wrong)

**Run with:** `go test ./api/... ./pkg/cmd/issue/...` *(verified)*

## Risks and open questions

- Does the `search` endpoint ever return a full page as its last page? If so, Option A
  costs one extra request in that case — acceptable, but worth stating in the PR.
- **For the maintainer:** should `--limit 0` continue to mean "unlimited"? PR #13913
  was rejected partly over this and the thread never resolved it.

## Contribution constraints

From `CONTRIBUTING.md` — read it, do not assume.

- Sign-off required (`git commit -s`); no CLA
- Conventional commit prefixes are not used here
- Maintainers ask that a linked issue exist before a PR — this one qualifies
- `make lint` must pass; CI runs `golangci-lint`

The single concrete action to start with — the file to open, the test to write first.

## Notes

- **Prior art is the differentiator.** An issue with three closed-unmerged PRs is not
  unclaimed easy work — it is work that keeps failing review. Find out why before
  recommending an approach, or repeat the same failure.
- **Root cause needs line numbers.** "The pagination logic is wrong" is a restatement.
  `queries_issue.go:224` is an analysis.
- **Acceptance criteria come from maintainer comments**, not from the issue body. The
  reporter says what hurts; the maintainer says what will be merged.
- **Say what could not be determined.** Every unresolved question here is one the
  implementer would otherwise hit blind.
